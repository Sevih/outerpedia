# Lots pour agents — mode d'emploi

> Comment déléguer un item du [TODO](./TODO.md) à un agent : un prompt complet
> par lot, écrit ici, lancé par le message type, relu avant d'être rangé. Ce
> fichier ne garde que l'outil ; un lot fait sort d'ici, sa trace est dans
> [DONE.md](./DONE.md) (93 lots du 25/09 au 07/10/2026, table des commits et
> leçons aux entrées du 04/10).
>
> Code d'un lot : A = une heure ou moins, B = une demi-journée, C = une
> journée, F = demande du jugement (agent Fable). Plusieurs lots tournent
> ensemble tant qu'ils ne touchent pas les mêmes fichiers ; ceux qui écrivent
> les six locales, les mêmes gros fichiers, ou qui lancent `datagen:build`
> passent un par un.

## Lancement — message type (le numéro du lot en dernier mot, sans point final)

Un agent ne lit que ce fichier : les règles communes sont dans le préambule de
chaque prompt, la réponse attendue aussi. Message à coller tel quel, en
remplaçant le dernier mot :

```text
Ouvre /home/sevih/Documents/Projet perso/outerpedia/docs/lots-opus-2026-09-25.md et lis UNIQUEMENT la section du lot dont le code est le dernier mot de ce message (ne lis pas les autres lots). Fais tout ce que son bloc demande, préambule compris. Ta réponse finale tient en une seule ligne : Demande <lot> : commit hash <hash>. Lot à faire : B2
```

Réponse attendue : `Demande B2 : commit hash 1a2b3c4d`. Tout le reste (résumé,
vérifications, ce qui est laissé) est dans l'entrée DONE du commit, c'est là
que la relecture le lit. Un agent bloqué répond `Demande B2 : bloque — …` avec
sa question et sa recommandation en une phrase.

```text
- `pnpm typecheck`, `pnpm lint`, `pnpm test` doivent passer. Cite la dernière ligne de chacun dans ton résumé.

2. Si l'item existe dans `docs/TODO.md`, retire-le (ou marque « FAIT » et ce qui reste, si la ligne porte d'autres points).

Écris ton entrée DONE juste avant ; si `docs/DONE.md` porte aussi l'entrée pas encore commitée d'un autre lot, commite quand même et signale-le dans ta réponse. <la tâche du lot>

Tâche : aujourd'hui chaque enregistrement de quick (`commitAndPush` dans `scripts/quick/actions.ts`, appelé par les codes promo, les 4-comics, les vidéos, les rangs, les recos) committe PUIS pousse `main`, donc lance la CI à chaque geste. Décision de Sevih du 08/10 : un enregistrement ne fait plus qu'un COMMIT local, sans rien demander ; le push est un geste à part, un bouton « Pousser » dans la barre d'en-tête de quick qui montre combien de commits attendent.

À lire d'abord : `scripts/quick/actions.ts` (le docblock de tête — « Les CINQ poussent quand même avec la CI » — et `commitAndPush`, `journal`, les interfaces `*Deps` qui le reçoivent en dépendance), `scripts/quick/server.ts` (`/api/state`, les routes POST, `json`), `scripts/quick/ui/lib.js` (`post`, `log`, `state`, les pastilles `service(...)` de l'en-tête, `sections`), `scripts/quick/ui/index.html` (le bloc `.status` de `<header class="top">` : pastilles R2 / YouTube / Discord, `#env`, « Quitter »), `scripts/quick/ui/STYLE.md` (la coquille, les boutons, le journal), `scripts/quick/shot.mjs` (`READ_ONLY_POSTS` : le banc ne relaie que ces POST), et les tests `scripts/quick/actions.test.ts` (les `deps({ git: … })`, les fausses `commitAndPush`) et `scripts/quick/ui-serve.test.ts`.

Ce qu'il faut faire :

1. Serveur, `actions.ts`. Remplace `commitAndPush` par DEUX fonctions, même journal (`journal(report)`), mêmes chemins EXPLICITES (jamais `git add -A`) :
   - `commitPaths(paths, message, report)` : `git add -- …`, rien d'indexé = « git : rien à committer. » (pas une erreur, comme aujourd'hui), puis `git commit` — la règle des hooks ne change pas (`--no-verify` seulement si tous les chemins sont du `.json`). Dernière ligne du journal : `git : <message>` puis `committé — N commit(s) à pousser (bouton « Pousser »)`, N venant de `gitState()`. Elle ne pousse JAMAIS.
   - `pushMain(report)` : `git push` de la branche courante. Hooks : même règle, calculée sur les fichiers des commits en attente (`git diff --name-only @{u}..HEAD`) — tout `.json` → `--no-verify`, sinon les hooks tournent (le pre-push fait un `tsc --noEmit` triple, une minute : le journal le dit AVANT, « pre-push : typecheck… »). Rien à pousser = « rien à pousser. » sans erreur. Échec = `git push a échoué : …` + « Corriger avec `git pull --rebase` puis « Pousser » de nouveau. » (les commits locaux restent, le dire). Succès = « poussé — la CI build et déploie. »
   - `gitState()` : `{ branch, ahead, behind }` par `git rev-list --left-right --count @{u}...HEAD` et `git rev-parse --abbrev-ref HEAD`, SANS `git fetch` (aucun réseau : `behind` est ce que le dépôt sait). Sans amont (`@{u}` absent) : `ahead: null`, et le bouton le dit.
   - Renomme les dépendances injectées (`commitAndPush` → `commitPaths`) dans les interfaces `*Deps`, les objets `*_DEPS` et les appels ; adapte les tests existants (les fausses `commitAndPush`, le message « git push a échoué » qui n'a plus sa place dans un enregistrement). Mets à jour le docblock de tête (les gestes committent ; le push est le bouton ; la règle « pas de [skip ci] » reste vraie pour le push) et celui de l'ancien `commitAndPush`.
2. Routes, `server.ts` : `/api/state` porte `git: gitState()` ; `GET /api/git` le rend seul ; `POST /api/push` appelle `pushMain` avec le journal (même mécanique de `report` que les autres POST longs) et répond `{ ok, log, git }`. Chaque POST d'enregistrement qui committe répond aussi `git` (l'état APRÈS le commit) — le plus simple : dans `server.ts`, après un `Outcome` ok de ces routes, ajouter `git: gitState()` au corps. `POST /api/push` N'ENTRE PAS dans `READ_ONLY_POSTS` de `shot.mjs` (le banc doit le refuser, vérifie-le dans le test du banc s'il y en a un, sinon dis-le dans le résumé).
3. Page. Dans `index.html`, dans `.status`, avant `#env` : `<button class="btn primary sm" id="push">Pousser <span class="badge" id="push-count">0</span></button>`. `lib.js` : une fonction `gitBar(git)` qui pose le compte, désactive le bouton à 0 (`title` « Rien à pousser »), le dit en retard si `behind > 0` (`title` « N commit(s) sur origin que tu n'as pas : `git pull --rebase` d'abord »), et « pas d'amont » si `ahead === null`. Appelée au démarrage (`/api/state`), et après CHAQUE `post()` réussi qui rend `git` (dans `post()` même : si la réponse porte `git`, `gitBar(git)` — aucune section n'a rien à faire). Clic : `busy` + désactivé, `post('/api/push')`, le journal suit (tiroir), puis `gitBar` avec l'état rendu. Charte : STYLE.md, `.btn.primary.sm`, un `.badge` dans le bouton ; ajoute à STYLE.md la ligne décrivant ce bouton dans l'en-tête.
4. Textes et confirmations. Tout ce qui promet un push à l'enregistrement est faux maintenant : `coupons.html` (« puis poussé : la CI rebâtit le site »), le journal de `addComics` (« poussé sur R2 » reste vrai, c'est R2 ; la suite git non), les messages des autres gestes, STYLE.md s'il en parle. Confirmations : SUPPRIME le `confirm` de `tabs/gear.js` qui garde l'enregistrement d'une liste vide (« Supprimer TOUTES les recos … committé et poussé ») — un commit local se défait, Sevih ne veut plus de confirmation avant un commit ; remplace-le par une ligne du journal (« gear-reco : <perso> retiré du fichier »). GARDE les `confirm` qui protègent une perte de saisie (quitter l'onglet avec des changements) et ceux de Discord (un envoi réel ne se défait pas). Liste dans le résumé chaque `confirm` restant et pourquoi.
5. Tests. `commitPaths`, `pushMain`, `gitState` se testent sur un DÉPÔT GIT JETABLE : `mkdtempSync` dans `tmpdir()`, `git init`, un remote `bare` dans le même dossier temporaire, un commit initial poussé, puis : un commit via `commitPaths` → `ahead: 1`, le journal dit « 1 commit à pousser » et le bare n'a PAS bougé ; `pushMain` → bare à jour, `ahead: 0`, journal « poussé » ; rien à pousser → « rien à pousser. » ; un commit poussé dans le bare par un autre clone → `behind: 1` et `pushMain` rend l'échec avec le conseil `pull --rebase` ; sans amont → `ahead: null`. Les fonctions prennent le `cwd` en option (défaut : le dépôt) pour ça — `spawnSync('git', args, { cwd })`. `user.name`/`user.email` posés dans le dépôt jetable (`git -c` ou `git config`), hooks absents là-bas donc `--no-verify` indifférent. La page : `ui-serve.test.ts` ou un test happy-dom (méthode C4) vérifie que `gitBar` pose le compte et l'état désactivé. Les tests existants adaptés passent.
6. Vérification : `pnpm typecheck && pnpm lint && pnpm test`, puis `NODE_ENV=development pnpm exec vitest run scripts/quick` (le `NODE_ENV` ambiant ne doit rien changer). Capture du banc : quick isolé (`DISCORD_BOT_TOKEN= DEV_PEERS= QUICK_PORT=<port libre> pnpm quick --no-open`), `node scripts/quick/shot.mjs --port <port> --tabs coupons --out /tmp/quick-shots/b33` : l'en-tête montre le bouton avec le compte réel du dépôt. Tu ne cliques JAMAIS « Pousser » sur ce quick, et tu n'enregistres rien dessus : le dépôt réel n'est touché que par tes commits de lot.

Hors périmètre : la liste des gestes qui committent (aucun nouveau), le contenu des messages de commit, `pnpm commit` et l'admin, un `git fetch` automatique, un `pull --rebase` depuis la page (Sevih le fait au terminal). Ne tourne pas en même temps qu'un autre lot sur `scripts/quick/` (ce lot touche `actions.ts`, `server.ts`, `lib.js`, `index.html` et plusieurs onglets).

Commit : `feat(quick): un enregistrement commite, « Pousser » dans la barre d'en-tête (B33)` — un seul commit, pas de push (jamais). Réponds `Demande B33 : commit hash <hash>` et un résumé : les `confirm` restants et pourquoi, les textes corrigés, ce que le banc a montré, et ce que tu as vu hors périmètre.
```
