# Lots pour agents — mode d'emploi

> Comment déléguer un item du [TODO](./TODO.md) à un agent : un prompt complet
> par lot, écrit ici, lancé par le message type, relu avant d'être rangé. Ce
> fichier ne garde que l'outil ; un lot fait sort d'ici, sa trace est dans
> [DONE.md](./DONE.md) (92 lots du 25/09 au 07/10/2026, table des commits et
> leçons aux entrées du 04/10).
>
> Code d'un lot : A = une heure ou moins, B = une demi-journée, C = une
> journée, F = demande du jugement (agent Fable). Plusieurs lots tournent
> ensemble tant qu'ils ne touchent pas les mêmes fichiers ; ceux qui écrivent
> les six locales, les mêmes gros fichiers, ou qui lancent `datagen:build`
> passent un par un.

## Lancement — message type (le numéro du lot en dernier mot, sans point final)

Un agent ne lit que ce fichier : les règles communes sont dans le préambule de
chaque prompt, la réponse attendue aussi. Message à coller tel quel, en
remplaçant le dernier mot :

```text
Ouvre /home/sevih/Documents/Projet perso/outerpedia/docs/lots-opus-2026-09-25.md et lis UNIQUEMENT la section du lot dont le code est le dernier mot de ce message (ne lis pas les autres lots). Fais tout ce que son bloc demande, préambule compris. Ta réponse finale tient en une seule ligne : Demande <lot> : commit hash <hash>. Lot à faire : B2
```

Réponse attendue : `Demande B2 : commit hash 1a2b3c4d`. Tout le reste (résumé,
vérifications, ce qui est laissé) est dans l'entrée DONE du commit, c'est là
que la relecture le lit. Un agent bloqué répond `Demande B2 : bloque — …` avec
sa question et sa recommandation en une phrase.

## Cap de quick (décision de Sevih du 07/10/2026)

`pnpm quick` (`scripts/quick/`) doit remplacer, à terme, tout ce qui dans
l'admin ne demande pas d'extraction : les éditeurs (persos, événements,
bannières, changelog, presets d'équipement, tags, effets…), les outils et
l'éditeur de guides — tout sauf les catégories « extractor » et « misc ». La
série UI de quick (C4, C5, B30, F16, B28, B29, C6, tous le 07/10) a posé ce
terrain : un menu horizontal à DEUX NIVEAUX (les groupes en haut — Publication,
Données, puis Éditeurs, Guides, Outils — et les sections du groupe en dessous ;
décision de Sevih du 07/10 : pas de barre latérale), une section = ses fichiers
`scripts/quick/ui/tabs/<nom>.{html,js,css}` et une entrée du tableau `GROUPS`
de `lib.js`, la charte dans `scripts/quick/ui/STYLE.md`, le banc de captures
`node scripts/quick/shot.mjs`. Un lot qui ajoute une section lit STYLE.md
d'abord et ne touche qu'à ses fichiers.

## B32 · Gear reco : les builds d'un perso en ONGLETS, comme sur la fiche perso (Opus)

Troisième retour de Sevih du 07/10 sur Gear reco : « plutôt que de mettre les différents builds les uns en dessous des autres, utiliser des tabs comme sur les fiches personnages ». Tourne seul (il touche `tabs/gear.*`).

```text
Tu travailles dans le dépôt `outerpedia` (Next.js + pipeline datagen), à la racine du projet, sur la branche `main`. Avant de toucher au code, lis `CONVENTIONS.md` et `CLAUDE.md` et respecte-les. Ce qui suit répond d'avance aux questions habituelles : ne les repose pas, applique.

Périmètre et méthode
- Périmètre STRICT à la tâche ci-dessous. Pas de refactor à côté, pas de « pendant que j'y suis ». Ce que tu repères hors périmètre va dans ton résumé, pas dans le diff.
- D'autres fichiers modifiés ou non suivis peuvent apparaître dans le working tree pendant ta session : ce sont d'autres lots qui tournent en parallèle. Ne les touche pas, ne les indexe pas, ne les signale pas, c'est attendu.
- Si la tâche cache une décision (métier, comportement ambigu, ordre de référence inconnu), arrête-toi AVANT de modifier quoi que ce soit et pose UNE question précise avec ta recommandation. Ne tranche pas toi-même.
- Toute clé i18n ajoutée l'est dans les SIX locales `src/i18n/locales/{en,fr,es,jp,kr,zh}.ts` (`keys.test.ts` exige la parité). Cherche une clé existante avant d'en créer une. Pour jp/kr/zh, traduction sobre ; en cas de doute, l'anglais, signalé dans le résumé.
- Ne touche jamais à `package.json` ni à `pnpm-lock.yaml`. Une version à monter ou à descendre est une décision : arrête-toi et pose la question (une montée de `next` validée sur typecheck, lint et tests a fait tomber la prod le 25/09).
- Ne lance jamais `pnpm dev`, `pnpm install`, `lefthook install`, ni un `git worktree add`. Si un serveur écoute déjà sur :3000, tu peux le lire avec `curl`. Si ta tâche exige de tester un hook git (commit d'essai, changement de branche), NE LE FAIS PAS toi-même : d'autres agents peuvent avoir des fichiers indexés dans cette arborescence et ton commit d'essai les emporterait. Prépare le changement, décris le test à faire, et laisse Sevih le jouer.

Vérification (obligatoire avant de rendre)
- `pnpm typecheck`, `pnpm lint`, `pnpm test` doivent passer. Cite la dernière ligne de chacun dans ton résumé.
- Aucun changement visuel non demandé ; quand la tâche en interdit, dis ce que tu as comparé.

Livraison (fais-la toi-même, sans demander)
1. Entrée dans `docs/DONE.md`, en TÊTE de la section du jour (`## 2026-MM-JJ`, crée-la si elle manque, sous le préambule du fichier) : une puce, titre en gras, puis le quoi, le pourquoi, le comment, la vérification, et ce que tu as laissé — dans le style des entrées voisines (français, prose dense, noms de fichiers en backticks).
2. Si l'item existe dans `docs/TODO.md`, retire-le (ou marque « FAIT » et ce qui reste, si la ligne porte d'autres points).
3. Commit par toi, en indexant EXPLICITEMENT et uniquement tes fichiers plus `docs/DONE.md` (et `docs/TODO.md` si touché). Jamais `git add -A`, jamais `git add .`. L'index git est PARTAGÉ avec les autres lots : indexe et commite dans UNE SEULE commande shell, précédée d'un contrôle — `test -z "$(git diff --cached --name-only)" && git add <tes chemins> && git commit -m "…"`. Si le contrôle échoue, un autre lot a des fichiers indexés : attends une minute et recommence, ne désindexe jamais ce qui n'est pas à toi. Écris ton entrée DONE juste avant ; si `docs/DONE.md` porte aussi l'entrée pas encore commitée d'un autre lot, commite quand même et signale-le dans ta réponse. Message en français, préfixe conventionnel (`fix(...)`, `refactor(...)`, `chore(...)`, `feat(...)`), une ligne, sans accents. Les hooks lefthook formatent et lintent ce qui est indexé : si le lint bloque, corrige et recommite. Pas de `--amend` sur un commit qui n'est pas le tien.
4. Pas de push.
5. Ta réponse finale tient en UNE ligne, rien d'autre : `Demande <lot> : commit hash <hash>` (`<lot>` = le code de ta section, ex. B2). Le résumé — fait, pourquoi, vérifié comment, laissé et pourquoi — va dans ton entrée DONE, pas dans ta réponse. Bloqué sur une décision : une ligne aussi, `Demande <lot> : bloque — <la question, en une phrase, avec ta recommandation>`.

Tâche :
Dans `pnpm quick` (`scripts/quick/`), l'onglet « Gear reco » (`scripts/quick/ui/tabs/gear.{html,js,css}`) empile les cartes des builds du perso dans `#g-list` (`gRender` les dessine toutes, `gRedraw(b)` en redessine une, `gCardEl(b)` retrouve la carte d'un build par sa clé `data-k`). Lis d'abord `scripts/quick/ui/STYLE.md` (la coquille : les sections d'un groupe sont des onglets `nav.tabs`, filet accent sous l'actif), les entrées DONE du 07/10 des lots B29, C7, C8, C9 et A29 et leurs relectures (l'onglet entier y est décrit), puis `gear.js` en entier — en particulier `gRender`, `gRedraw`, `gBar`, `gCardEl` et TOUS ses appelants, le `onclick` de `#g-list` (actions `dup`, `up`, `down`, `del`, `translate`), `gPvAsk` et le rendu de l'aperçu, `loadGear` et l'analyse du hash en bas du fichier (`#gear/<id>`, `#gear/<id>/picker/<slot>`). Côté site, `GearRecoSection` (`src/components/character/GearRecoSection.tsx`) montre UN build à la fois derrière une rangée d'onglets (`gameTabClass`) : c'est le modèle demandé, pour le mécanisme — le style reste celui de quick.

Objectif.

1. Une rangée d'onglets (`role="tablist"`) entre la savebar et la carte, un onglet (`button[role="tab"]`, `aria-selected`, `aria-controls`) par build, dans l'ordre des builds : son nom, ou « Build n » s'il est vide. Un build MODIFIÉ et non enregistré porte un point (le même critère que le compteur de la savebar, `gBase`) ; un build en erreur (une `issue` de `gIssues` ou un refus du serveur `gServer`) porte un point rouge, pour qu'un onglet caché ne cache jamais une erreur. Le style reprend celui des sections de la coquille (filet accent sous l'actif, texte atténué pour les autres), en plus compact (32 px) ; si les classes de `quick.css` ne se prêtent pas à être réutilisées hors de la coquille, des classes `.g-tabs*` dans `gear.css` qui les miment. Sans build : pas de rangée, le message `.empty` d'aujourd'hui.

2. UNE seule carte rendue dans `#g-list` : celle du build actif (`gActive`, un index en mémoire de page, 0 à l'ouverture d'un perso). Clavier dans la rangée : flèches gauche / droite, Début / Fin, focus roulant (`tabindex` 0 sur l'actif, -1 ailleurs). Les gestes existants suivent : « ＋ build » ajoute ET active le nouveau ; « Dupliquer » insère la copie après l'original et l'active ; « Monter » / « Descendre » déplacent le build et l'onglet le suit (il reste actif) ; « Supprimer » (sa confirmation d'aujourd'hui) active le voisin précédent, ou le premier ; « Annuler » garde l'index, borné au nombre de builds ; changer de perso remet 0. « Traduire » continue de traduire TOUS les builds du perso ; son erreur et le compteur de caractères ne se montrent que dans la carte active (les écritures dans `[data-tr-error]` / `[data-len]` tolèrent l'absence des autres cartes). Audite chaque appelant de `gCardEl` : pour un build non actif il rend `null`, rien ne doit planter — `gRedraw` d'un build caché se contente de rafraîchir la rangée d'onglets et la savebar.

3. L'aperçu (C9) : UNE requête pour tous les builds comme aujourd'hui, mais seul le bloc de la carte active est rendu ; la dernière réponse est gardée par clé de build, et changer d'onglet redessine depuis elle SANS nouvelle requête (une requête ne part que si la charge a changé, règle actuelle). L'état replié / déplié du bloc d'aperçu et des « Traductions » reste par build (les `Set` existants, par clé).

4. Le hash : `#gear/<id>/build/<n>` (n à partir de 1) ouvre le perso sur ce build ; combiné : `#gear/<id>/build/<n>/picker/<slot>`. Le picker du hash s'ouvre sur le build ACTIF (aujourd'hui `gBuilds[0]`). La page n'écrit pas le hash à chaque changement d'onglet (règle de `lib.js`, qui le réécrit à la bascule de section) — c'est une entrée pour le banc et les liens. `STYLE.md` : le croquis de Gear reco dit la rangée d'onglets et le hash.

Hors périmètre : le contenu des cartes, les pickers, l'aperçu lui-même, le serveur, le site.

Décisions déjà prises (ne les repose pas) : un seul build visible à la fois, pas de mode « tout déplier » ; les boutons Dupliquer / Monter / Descendre / Supprimer restent dans la tête de la carte ; le badge « 1 / 3 » de la tête de carte disparaît (la rangée le dit) ; style des onglets = celui des sections de la coquille, pas le « glow » du site.

Vérification propre au lot : outre typecheck, lint et tests, (a) la logique jouée dans happy-dom hors du dépôt derrière un relais en lecture seule (la recette des lots C7 à C9 ; le `POST` d'enregistrement n'est JAMAIS transmis) — au moins : une seule carte au chargement, l'onglet 2 cliqué montre le build 2, flèches et Début / Fin, « ＋ build » active le nouveau, « Dupliquer » active la copie à la bonne place, « Descendre » déplace l'onglet actif, « Supprimer » active le voisin, un changement sur le build 1 puis l'onglet 2 → point sur l'onglet 1 et compteur de la savebar inchangé, une stat retirée → point rouge, « Annuler » efface les points, changer d'onglet ne relance pas l'aperçu, `#gear/<id>/build/2/picker/weapons` ouvre le picker sur le build 2 ; (b) le banc sur un quick isolé (`DISCORD_BOT_TOKEN= DEV_PEERS= QUICK_PORT=<un autre port> pnpm quick --no-open`, JAMAIS un enregistrement réel : chaque enregistrement de quick committe ET pousse `main`) : `node scripts/quick/shot.mjs --port <port> --tabs gear --out /tmp/quick-shots/b32 --hash gear/2000055 --size 1440x1900` puis `--hash gear/2000055/build/2` (Aer, trois builds) — la rangée, l'onglet actif, une seule carte ; cite les chemins des PNG dans ton entrée DONE.

Ne tourne avec aucun autre lot qui touche `scripts/quick/`.
```
