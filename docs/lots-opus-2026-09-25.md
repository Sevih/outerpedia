# Lots pour agents — mode d'emploi

> Comment déléguer un item du [TODO](./TODO.md) à un agent : un prompt complet
> par lot, écrit ici, lancé par le message type, relu avant d'être rangé. Ce
> fichier ne garde que l'outil ; un lot fait sort d'ici, sa trace est dans
> [DONE.md](./DONE.md) (80 lots du 25/09 au 06/10/2026, table des commits et
> leçons aux entrées du 04/10).
>
> Code d'un lot : A = une heure ou moins, B = une demi-journée, C = une
> journée, F = demande du jugement (agent Fable). Plusieurs lots tournent
> ensemble tant qu'ils ne touchent pas les mêmes fichiers ; ceux qui écrivent
> les six locales, les mêmes gros fichiers, ou qui lancent `datagen:build`
> passent un par un.

## Lancement — message type (le numéro du lot en dernier mot, sans point final)

Un agent ne lit que ce fichier : les règles communes sont dans le préambule de
chaque prompt, la réponse attendue aussi. Message à coller tel quel, en
remplaçant le dernier mot :

```text
Ouvre /home/sevih/Documents/Projet perso/outerpedia/docs/lots-opus-2026-09-25.md et lis UNIQUEMENT la section du lot dont le code est le dernier mot de ce message (ne lis pas les autres lots). Fais tout ce que son bloc demande, préambule compris. Ta réponse finale tient en une seule ligne : Demande <lot> : commit hash <hash>. Lot à faire : B2
```

Réponse attendue : `Demande B2 : commit hash 1a2b3c4d`. Tout le reste (résumé,
vérifications, ce qui est laissé) est dans l'entrée DONE du commit, c'est là
que la relecture le lit. Un agent bloqué répond `Demande B2 : bloque — …` avec
sa question et sa recommandation en une phrase.

## C4 · quick, onglet « Gear reco » : éditer les recos d'équipement d'un perso et publier

```text
Tu travailles dans le dépôt `outerpedia` (Next.js + pipeline datagen), à la racine du projet, sur la branche `main`. Avant de toucher au code, lis `CONVENTIONS.md` et `CLAUDE.md` et respecte-les. Ce qui suit répond d'avance aux questions habituelles : ne les repose pas, applique.

Périmètre et méthode
- Périmètre STRICT à la tâche ci-dessous. Pas de refactor à côté, pas de « pendant que j'y suis ». Ce que tu repères hors périmètre va dans ton résumé, pas dans le diff.
- D'autres fichiers modifiés ou non suivis peuvent apparaître dans le working tree pendant ta session : ce sont d'autres lots qui tournent en parallèle. Ne les touche pas, ne les indexe pas, ne les signale pas, c'est attendu.
- Si la tâche cache une décision (métier, comportement ambigu, ordre de référence inconnu), arrête-toi AVANT de modifier quoi que ce soit et pose UNE question précise avec ta recommandation. Ne tranche pas toi-même.
- Toute clé i18n ajoutée l'est dans les SIX locales `src/i18n/locales/{en,fr,es,jp,kr,zh}.ts` (`keys.test.ts` exige la parité). Cherche une clé existante avant d'en créer une. Pour jp/kr/zh, traduction sobre ; en cas de doute, l'anglais, signalé dans le résumé.
- Ne touche jamais à `package.json` ni à `pnpm-lock.yaml`. Une version à monter ou à descendre est une décision : arrête-toi et pose la question (une montée de `next` validée sur typecheck, lint et tests a fait tomber la prod le 25/09).
- Ne lance jamais `pnpm dev`, `pnpm install`, `lefthook install`, ni un `git worktree add`. Si un serveur écoute déjà sur :3000, tu peux le lire avec `curl`. Si ta tâche exige de tester un hook git (commit d'essai, changement de branche), NE LE FAIS PAS toi-même : d'autres agents peuvent avoir des fichiers indexés dans cette arborescence et ton commit d'essai les emporterait. Prépare le changement, décris le test à faire, et laisse Sevih le jouer.

Vérification (obligatoire avant de rendre)
- `pnpm typecheck`, `pnpm lint`, `pnpm test` doivent passer. Cite la dernière ligne de chacun dans ton résumé.
- Aucun changement visuel non demandé ; quand la tâche en interdit, dis ce que tu as comparé.

Livraison (fais-la toi-même, sans demander)
1. Entrée dans `docs/DONE.md`, en TÊTE de la section du jour (`## 2026-MM-JJ`, crée-la si elle manque, sous le préambule du fichier) : une puce, titre en gras, puis le quoi, le pourquoi, le comment, la vérification, et ce que tu as laissé — dans le style des entrées voisines (français, prose dense, noms de fichiers en backticks).
2. Si l'item existe dans `docs/TODO.md`, retire-le (ou marque « FAIT » et ce qui reste, si la ligne porte d'autres points).
3. Commit par toi, en indexant EXPLICITEMENT et uniquement tes fichiers plus `docs/DONE.md` (et `docs/TODO.md` si touché). Jamais `git add -A`, jamais `git add .`. L'index git est PARTAGÉ avec les autres lots : indexe et commite dans UNE SEULE commande shell, précédée d'un contrôle — `test -z "$(git diff --cached --name-only)" && git add <tes chemins> && git commit -m "…"`. Si le contrôle échoue, un autre lot a des fichiers indexés : attends une minute et recommence, ne désindexe jamais ce qui n'est pas à toi. Écris ton entrée DONE juste avant ; si `docs/DONE.md` porte aussi l'entrée pas encore commitée d'un autre lot, commite quand même et signale-le dans ta réponse. Message en français, préfixe conventionnel (`fix(...)`, `refactor(...)`, `chore(...)`, `feat(...)`), une ligne, sans accents. Les hooks lefthook formatent et lintent ce qui est indexé : si le lint bloque, corrige et recommite. Pas de `--amend` sur un commit qui n'est pas le tien.
4. Pas de push.
5. Ta réponse finale tient en UNE ligne, rien d'autre : `Demande <lot> : commit hash <hash>` (`<lot>` = le code de ta section, ex. B2). Le résumé — fait, pourquoi, vérifié comment, laissé et pourquoi — va dans ton entrée DONE, pas dans ta réponse. Bloqué sur une décision : une ligne aussi, `Demande <lot> : bloque — <la question, en une phrase, avec ta recommandation>`.

Tâche :
Les recommandations d'équipement des persos (`data/curated/gear-reco.json` : 95 persos, 265 builds, 91 notes) s'éditent aujourd'hui dans l'admin (`/admin/editor/characters/<id>`, `src/components/admin/GearRecoEditor.tsx`, route `src/app/api/admin/curated/gear-reco/[id]/route.dev.ts`), qui écrit le fichier mais ne commite pas : Sevih finit au terminal, à la main (`d31459ea`, « gdomine fix », le 06/10). Demande du 07/10/2026 : un onglet « Gear reco » dans `pnpm quick` (`scripts/quick/`), l'outil local dont chaque geste commite ET pousse — éditer les builds d'un perso puis publier, comme l'onglet « Rangs » le fait pour les rangs.

Lis d'abord, en entier : `scripts/quick/server.ts` (routes, `stream()`, gardes `lan.ts`), `scripts/quick/actions.ts` (surtout `rankState`, `planRankChanges`, `saveRanks`, `commitAndPush` et son en-tête — chemins EXPLICITES, jamais `git add -A`), `scripts/quick/actions.test.ts` (comment un enregistrement est testé SANS écrire dans le dépôt ni pousser), l'onglet « Rangs » de `scripts/quick/ui.html` (`#tab-ranks`, `renderRanks`, `loadRanks`, la barre d'enregistrement qui suit le défilement, les états `dirty`/`refused`), `src/lib/admin/gear-reco-store.ts` (`upsertGearReco` : recompression des presets par `collapseBuild`, `validateGearBuilds`, écriture triée sous verrou — c'est LUI qui écrit, tu ne réécris pas une écriture), `datagen/curated/gear-reco.ts` (`validateGearBuilds` : ce qu'il refuse), `src/lib/data/gear-reco.ts` (`loadGearReco`, `loadGearPresets`, types `GearBuild`/`GearPick`/`SetCombo` du module `@contracts`, cf. l'alias de `tsconfig.json`), `src/lib/admin/gear-options.ts` (`gearSelectOptions` : les listes d'armes, d'amulettes, de talismans et de sets avec les `mainStats` permis par pièce — générées, « plus de fautes de frappe possibles »), `src/lib/admin/gear-preset-resolve.ts` (déplier/replier `$preset`), `data/curated/gear-presets.json` (son `_doc` : talismans 35, sets 41, substats 20 — les presets s'éditent dans l'admin, PAS ici), `src/lib/admin/tag-control.ts` et son test (un tag `{I-T/…}` inconnu dans une note fait ÉCHOUER la suite), et l'entrée DONE du lot B19 (onglet « Rangs », 04/10) pour la forme.

À faire :
1. ROUTES dans `server.ts`, mêmes gardes que les autres : `GET /api/gear-reco/state` — le roster (`getCharacterListItems`, nom, id, et s'il a des recos), les presets (lecture seule, dépliés pour affichage), les options des sélecteurs (`gearSelectOptions`), et les builds d'un perso en PIÈCES (presets dépliés, comme l'admin les édite — `?id=`) ; `POST /api/gear-reco` `{ id, builds }` → l'enregistrement du point 3, en NDJSON (`stream()`), journal au fil de l'eau.
2. ONGLET « Gear reco » dans `ui.html`, après « Rangs » : un sélecteur de perso (recherche par nom, ceux qui ont des recos marqués), puis la liste de ses builds. Un build = nom (texte), armes (0..n : pièce dans une liste déroulante tirée des options, stat principale dans la liste des `mainStats` permis par CETTE pièce), amulettes (idem), talismans (un preset `$slug` dans une liste, OU des pièces une à une), sets (un preset OU des paires set + nombre), substats (un preset OU un texte libre `ATK>SPD>HP`), note en / fr / es (les trois langues des notes existantes ; jp / kr / zh optionnelles, vides par défaut). Boutons : ajouter / dupliquer / supprimer / monter / descendre un build, ajouter / retirer une pièce. Même langage visuel que « Rangs » : états `dirty`, erreurs de validation affichées à la pièce ou au build, barre d'enregistrement fixe avec le compte de changements ; quitter l'onglet avec des changements non enregistrés demande confirmation. Aucune prévisualisation en tuiles : c'est l'admin qui rend, quick édite la donnée.
3. ENREGISTREMENT (`actions.ts`, fonction `saveGearReco(id, builds, deps, report)`) : `upsertGearReco(id, builds)` (il valide, replie les presets, écrit trié sous verrou) ; s'il rend des erreurs → rien n'est commité, elles reviennent dans le journal ET à l'écran ; sinon `commitAndPush(['data/curated/gear-reco.json'], 'chore(gear-reco): <nom du perso>', report)`. Les tags inline des notes sont contrôlés AVANT l'écriture avec la même résolution que `tag-control.ts` (un tag inconnu = erreur affichée, pas un commit qui casse la suite). Un perso dont on supprime tous les builds : `upsertGearReco` retire la clé — demande une confirmation explicite côté page.
4. TESTS (`actions.test.ts` ou un fichier à côté) : `saveGearReco` avec un `upsert` et un `commitAndPush` INJECTÉS — erreurs de validation → aucun commit ; succès → le seul chemin `data/curated/gear-reco.json` et le message attendu ; tag inconnu dans une note → refus avant écriture ; dépliage/repliage des presets aller-retour sans perte sur trois builds réels du fichier (lus, jamais écrits). Pas de test qui écrit dans `data/curated/` ni ne lance git.

Sécurité, impérativement : tu n'enregistres JAMAIS depuis la page — chaque enregistrement réel COMMITE ET POUSSE `main`, donc déploie. Pour essayer l'onglet, lance quick ainsi, dans un terminal à part : `DISCORD_BOT_TOKEN= DEV_PEERS= QUICK_PORT=4799 pnpm quick --no-open`, lis la page et `GET /api/gear-reco/state` par `curl`, et n'appelle JAMAIS le POST autrement que par les tests avec lanceur factice. Dis dans l'entrée DONE ce que tu as joué. `gear-presets.json` ne se modifie pas d'ici.

Hors périmètre : l'éditeur de l'admin (il reste la surface de rendu), les presets, les autres onglets, le rendu des recos sur le site.

Ce lot tourne SEUL sur `scripts/quick/` (il touche `ui.html`, `server.ts`, `actions.ts`). Code C : une journée.
```
