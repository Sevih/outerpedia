# Lots pour agents — mode d'emploi

> Comment déléguer un item du [TODO](./TODO.md) à un agent : un prompt complet
> par lot, écrit ici, lancé par le message type, relu avant d'être rangé. Ce
> fichier ne garde que l'outil ; un lot fait sort d'ici, sa trace est dans
> [DONE.md](./DONE.md) (65 lots du 25/09 au 05/10/2026, table des commits et
> leçons aux entrées du 04/10).
>
> Code d'un lot : A = une heure ou moins, B = une demi-journée, C = une
> journée, F = demande du jugement (agent Fable). Plusieurs lots tournent
> ensemble tant qu'ils ne touchent pas les mêmes fichiers ; ceux qui écrivent
> les six locales, les mêmes gros fichiers, ou qui lancent `datagen:build`
> passent un par un.

## Lancement — message type (le numéro du lot en dernier mot, sans point final)

Un agent ne lit que ce fichier : les règles communes sont dans le préambule de
chaque prompt, la réponse attendue aussi. Message à coller tel quel, en
remplaçant le dernier mot :

```text
Ouvre /home/sevih/Documents/Projet perso/outerpedia/docs/lots-opus-2026-09-25.md et lis UNIQUEMENT la section du lot dont le code est le dernier mot de ce message (ne lis pas les autres lots). Fais tout ce que son bloc demande, préambule compris. Ta réponse finale tient en une seule ligne : Demande <lot> : commit hash <hash>. Lot à faire : B2
```

Réponse attendue : `Demande B2 : commit hash 1a2b3c4d`. Tout le reste (résumé,
vérifications, ce qui est laissé) est dans l'entrée DONE du commit, c'est là
que la relecture le lit. Un agent bloqué répond `Demande B2 : bloque — …` avec
sa question et sa recommandation en une phrase.

## F12 · Portraits animés : un nouvel effet arrive sans geste manuel

```text
Tu travailles dans le dépôt `outerpedia` (Next.js + pipeline datagen), à la racine du projet, sur la branche `main`. Avant de toucher au code, lis `CONVENTIONS.md` et `CLAUDE.md` et respecte-les. Ce qui suit répond d'avance aux questions habituelles : ne les repose pas, applique.

Périmètre et méthode
- Périmètre STRICT à la tâche ci-dessous. Pas de refactor à côté, pas de « pendant que j'y suis ». Ce que tu repères hors périmètre va dans ton résumé, pas dans le diff.
- D'autres fichiers modifiés ou non suivis peuvent apparaître dans le working tree pendant ta session : ce sont d'autres lots qui tournent en parallèle. Ne les touche pas, ne les indexe pas, ne les signale pas, c'est attendu.
- Si la tâche cache une décision (métier, comportement ambigu, ordre de référence inconnu), arrête-toi AVANT de modifier quoi que ce soit et pose UNE question précise avec ta recommandation. Ne tranche pas toi-même.
- Toute clé i18n ajoutée l'est dans les SIX locales `src/i18n/locales/{en,fr,es,jp,kr,zh}.ts` (`keys.test.ts` exige la parité). Cherche une clé existante avant d'en créer une. Pour jp/kr/zh, traduction sobre ; en cas de doute, l'anglais, signalé dans le résumé.
- Ne touche jamais à `package.json` ni à `pnpm-lock.yaml`. Une version à monter ou à descendre est une décision : arrête-toi et pose la question (une montée de `next` validée sur typecheck, lint et tests a fait tomber la prod le 25/09).
- Ne lance jamais `pnpm dev`, `pnpm install`, `lefthook install`, ni un `git worktree add`. Si un serveur écoute déjà sur :3000, tu peux le lire avec `curl`. Si ta tâche exige de tester un hook git (commit d'essai, changement de branche), NE LE FAIS PAS toi-même : d'autres agents peuvent avoir des fichiers indexés dans cette arborescence et ton commit d'essai les emporterait. Prépare le changement, décris le test à faire, et laisse Sevih le jouer.

Vérification (obligatoire avant de rendre)
- `pnpm typecheck`, `pnpm lint`, `pnpm test` doivent passer. Cite la dernière ligne de chacun dans ton résumé.
- Aucun changement visuel non demandé ; quand la tâche en interdit, dis ce que tu as comparé.

Livraison (fais-la toi-même, sans demander)
1. Entrée dans `docs/DONE.md`, en TÊTE de la section du jour (`## 2026-MM-JJ`, crée-la si elle manque, sous le préambule du fichier) : une puce, titre en gras, puis le quoi, le pourquoi, le comment, la vérification, et ce que tu as laissé — dans le style des entrées voisines (français, prose dense, noms de fichiers en backticks).
2. Si l'item existe dans `docs/TODO.md`, retire-le (ou marque « FAIT » et ce qui reste, si la ligne porte d'autres points).
3. Commit par toi, en indexant EXPLICITEMENT et uniquement tes fichiers plus `docs/DONE.md` (et `docs/TODO.md` si touché). Jamais `git add -A`, jamais `git add .`. L'index git est PARTAGÉ avec les autres lots : indexe et commite dans UNE SEULE commande shell, précédée d'un contrôle — `test -z "$(git diff --cached --name-only)" && git add <tes chemins> && git commit -m "…"`. Si le contrôle échoue, un autre lot a des fichiers indexés : attends une minute et recommence, ne désindexe jamais ce qui n'est pas à toi. Écris ton entrée DONE juste avant ; si `docs/DONE.md` porte aussi l'entrée pas encore commitée d'un autre lot, commite quand même et signale-le dans ta réponse. Message en français, préfixe conventionnel (`fix(...)`, `refactor(...)`, `chore(...)`, `feat(...)`), une ligne, sans accents. Les hooks lefthook formatent et lintent ce qui est indexé : si le lint bloque, corrige et recommite. Pas de `--amend` sur un commit qui n'est pas le tien.
4. Pas de push.
5. Ta réponse finale tient en UNE ligne, rien d'autre : `Demande <lot> : commit hash <hash>` (`<lot>` = le code de ta section, ex. B2). Le résumé — fait, pourquoi, vérifié comment, laissé et pourquoi — va dans ton entrée DONE, pas dans ta réponse. Bloqué sur une décision : une ligne aussi, `Demande <lot> : bloque — <la question, en une phrase, avec ta recommandation>`.

Tâche :
Demande de Sevih (05/10) : quand le jeu sort un perso avec un NOUVEL effet de portrait, l'effet doit arriver sur le site sans geste manuel, comme `_Resonance` (Resonance Rin, commit `4c58b85a`) qui « se servait tel quel » mais a quand même demandé qu'on l'inscrive à la main. NE COMMENCE PAS tant que le lot F11 (contexte WebGL partagé) n'est pas committé : `git log --oneline -15` doit le montrer, sinon réponds `bloque — F11 pas encore committé`. Tu pars de son code.

Lis d'abord : `datagen/assets/extract-portrait-fx.py` en entier (son en-tête, `DEFAULT_EFFECTS`, `by_character`, `unextracted`, l'avertissement final), l'étape `portrait-fx` de `datagen/refresh.ts`, `src/components/character/portrait-fx.ts` (`fxOf`, `fxNameOf`), `layerVerdict` dans `portrait-fx-sim.ts`, `portrait-fx.test.ts` (son en-tête dit le contrat d'aujourd'hui), `AnimatedPortrait.tsx`, `src/app/dev/AnimatedPortrait/page.dev.tsx`, `docs/audit/portrait-fx.md` (P4, P7, P8), et le commit `4c58b85a` pour voir ce qu'un ajout a coûté.

Ce qui est manuel aujourd'hui, à l'arrivée d'un effet : (1) inscrire son suffixe dans `DEFAULT_EFFECTS`, faute de quoi il n'est pas extrait et `pnpm test` casse (`NOT_EXTRACTED`) — donc le patch est bloqué ; (2) si un de ses calques est refusé par le moteur, inscrire le refus dans `NOT_RENDERED` ou transcrire, faute de quoi `pnpm test` casse aussi ; (3) écrire sa section sur la page de contrôle.

La cible, décidée :
1. EXTRACTION SANS LISTE. Les effets extraits sont ceux que la table du jeu nomme (`CharacterExtraTemplet.ThumbnailEffect`, tout `byCharacter`) et dont le prefab existe dans le bundle ; `DEFAULT_EFFECTS` disparaît comme source (les arguments en ligne de commande et `--all` restent pour le travail à la main). Table parsée absente : le script ne réécrit PAS une table vide ni tronquée, il garde le `byCharacter` et la liste d'effets du JSON committé et le dit (c'est P8, solde-le ici).
2. SERVI SEULEMENT SI ENTIER. Un effet dont TOUS les calques actifs passent `layerVerdict` est servi sans aucun geste. Un effet dont un calque actif est refusé (branche de shader, module ou mode non transcrit) n'est PAS servi à moitié : le perso garde son portrait statique, c'est la règle de la maison (« refuser plutôt que rendre de travers »). Cette mise en attente est calculée, pas tenue à la main : une fonction pure, mémoïsée par nom d'effet, que `fxOf`/`AnimatedPortrait` consultent, et qui ne monte ni contexte ni canvas pour un effet en attente. `NOT_RENDERED` devient la liste des refus ACCEPTÉS (décision prise de servir l'effet sans ce calque), lue par cette même fonction et par le test — une seule liste, à côté du moteur, plus dans le fichier de test.
3. UN PATCH N'EST JAMAIS BLOQUÉ PAR UN EFFET QUI ARRIVE. Le test de contrat ne casse plus sur un effet nouveau, rendable ou non ; il continue de casser sur ce qui est une vraie panne : table vide, espace colorimétrique, texture ou maille incohérente, refus accepté devenu faux, et un effet servi au commit précédent qui ne le serait plus alors que sa fiche n'a pas changé (à toi de trouver comment le dire sans figer une liste à la main — sinon explique pourquoi tu y renonces).
4. ÇA SE VOIT QUAND MÊME. Le refresh dit, pour chaque effet NOUVEAU par rapport à la table committée : son nom, ses porteurs, et « servi tel quel » ou « en attente : <effet>/<calque> — <motif de layerVerdict> ». Le verdict est en TypeScript et l'extraction en Python : ajoute au refresh le petit pas qu'il faut après `portrait-fx`, sans réécrire `layerVerdict` en Python. Un effet en attente ne fait pas échouer le refresh ; il sort dans son récapitulatif final, là où Sevih le lit.
5. PAGE DE CONTRÔLE. Tout effet de la table qui n'a pas de section écrite à la main y apparaît seul, dans une section générique (ses porteurs, la carte animée, ses calques avec leur verdict), et les effets en attente y sont listés avec leur motif. Les sections existantes ne bougent pas.

Hors périmètre : transcrire une branche de shader ou un module (un effet en attente le reste, c'est le but), les autres gardes de P7, le rendu lui-même (`portrait-fx-gl.ts` n'est touché que si la fonction de mise en attente doit y être lue), le plafond des textures. Ne relance PAS l'extraction pour committer une table régénérée : elle ne doit pas changer d'un octet aujourd'hui (les dix effets nommés sont déjà les dix extraits) — vérifie-le en la rejouant si `.gamedata` est là, sinon dis que tu ne l'as pas pu.

Vérification propre au lot :
- Simule l'arrivée d'un effet, sans toucher aux fichiers committés (copie de la table dans un dossier temporaire, ou fixtures de test) : (a) un perso de plus qui nomme un effet rendable → servi, test vert, annoncé « servi tel quel » ; (b) un effet dont un calque porte un mot-clé que le moteur refuse → en attente, portrait statique, test vert, annoncé avec son motif ; (c) un effet nommé sans prefab dans le bundle → signalé, rien ne casse ; (d) table parsée absente → JSON committé inchangé.
- Tests de la fonction de mise en attente et du pas de rapport.
- Si un serveur écoute sur :3000, lis `/dev/AnimatedPortrait` (une requête, pas de boucle) pour confirmer que la page rend toujours ; aucun contrôle visuel n'est attendu de toi, le rendu ne change pas.
- Dans ton entrée DONE : « ce que Sevih fait quand un nouvel effet arrive » en trois cas (servi tel quel : rien ; en attente : quoi lire et où transcrire ; absent du bundle : quoi vérifier), et ce que le prochain patch prouvera que tu n'as pas pu prouver.
- Ajoute au TODO, section « À jouer au prochain patch », une ligne : contrôler le rapport du refresh au premier patch qui apporte un effet.

Ce lot tourne SEUL et APRÈS F11 : il partage `portrait-fx.test.ts`, `AnimatedPortrait.tsx` et la page de contrôle avec lui.
```
