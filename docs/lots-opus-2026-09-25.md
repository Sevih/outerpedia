# Lots pour agents — mode d'emploi

> Comment déléguer un item du [TODO](./TODO.md) à un agent : un prompt complet
> par lot, écrit ici, lancé par le message type, relu avant d'être rangé. Ce
> fichier ne garde que l'outil ; un lot fait sort d'ici, sa trace est dans
> [DONE.md](./DONE.md) (72 lots du 25/09 au 05/10/2026, table des commits et
> leçons aux entrées du 04/10).
>
> Code d'un lot : A = une heure ou moins, B = une demi-journée, C = une
> journée, F = demande du jugement (agent Fable). Plusieurs lots tournent
> ensemble tant qu'ils ne touchent pas les mêmes fichiers ; ceux qui écrivent
> les six locales, les mêmes gros fichiers, ou qui lancent `datagen:build`
> passent un par un.

## Lancement — message type (le numéro du lot en dernier mot, sans point final)

Un agent ne lit que ce fichier : les règles communes sont dans le préambule de
chaque prompt, la réponse attendue aussi. Message à coller tel quel, en
remplaçant le dernier mot :

```text
Ouvre /home/sevih/Documents/Projet perso/outerpedia/docs/lots-opus-2026-09-25.md et lis UNIQUEMENT la section du lot dont le code est le dernier mot de ce message (ne lis pas les autres lots). Fais tout ce que son bloc demande, préambule compris. Ta réponse finale tient en une seule ligne : Demande <lot> : commit hash <hash>. Lot à faire : B2
```

Réponse attendue : `Demande B2 : commit hash 1a2b3c4d`. Tout le reste (résumé,
vérifications, ce qui est laissé) est dans l'entrée DONE du commit, c'est là
que la relecture le lit. Un agent bloqué répond `Demande B2 : bloque — …` avec
sa question et sa recommandation en une phrase.

## F14 · Revue d'extraction : les retouches mineures (costumes, textes) passent sans ré-intégration

```text
Tu travailles dans le dépôt `outerpedia` (Next.js + pipeline datagen), à la racine du projet, sur la branche `main`. Avant de toucher au code, lis `CONVENTIONS.md` et `CLAUDE.md` et respecte-les. Ce qui suit répond d'avance aux questions habituelles : ne les repose pas, applique.

Périmètre et méthode
- Périmètre STRICT à la tâche ci-dessous. Pas de refactor à côté, pas de « pendant que j'y suis ». Ce que tu repères hors périmètre va dans ton résumé, pas dans le diff.
- D'autres fichiers modifiés ou non suivis peuvent apparaître dans le working tree pendant ta session : ce sont d'autres lots qui tournent en parallèle. Ne les touche pas, ne les indexe pas, ne les signale pas, c'est attendu.
- Si la tâche cache une décision (métier, comportement ambigu, ordre de référence inconnu), arrête-toi AVANT de modifier quoi que ce soit et pose UNE question précise avec ta recommandation. Ne tranche pas toi-même.

Si ta tâche exige de tester un hook git (commit d'essai, changement de branche), NE LE FAIS PAS toi-même : d'autres agents peuvent avoir des fichiers indexés dans cette arborescence et ton commit d'essai les emporterait. Prépare le changement, décris le test à faire, et laisse Sevih le jouer.

Vérification (obligatoire avant de rendre)
- `pnpm typecheck`, `pnpm lint`, `pnpm test` doivent passer. Cite la dernière ligne de chacun dans ton résumé.
- Aucun changement visuel non demandé ; quand la tâche en interdit, dis ce que tu as comparé.

Livraison (fais-la toi-même, sans demander)
1. Entrée dans `docs/DONE.md`, en TÊTE de la section du jour (`## 2026-MM-JJ`, crée-la si elle manque, sous le préambule du fichier) : une puce, titre en gras, puis le quoi, le pourquoi, le comment, la vérification, et ce que tu as laissé — dans le style des entrées voisines (français, prose dense, noms de fichiers en backticks).
2. Si l'item existe dans `docs/TODO.md`, retire-le (ou marque « FAIT » et ce qui reste, si la ligne porte d'autres points).
3. Commit par toi, en indexant EXPLICITEMENT et uniquement tes fichiers plus `docs/DONE.md` (et `docs/TODO.md` si touché). Jamais `git add -A`, jamais `git add .`. L'index git est PARTAGÉ avec les autres lots : indexe et commite dans UNE SEULE commande shell, précédée d'un contrôle — `test -z "$(git diff --cached --name-only)" && git add <tes chemins> && git commit -m "…"`. Si le contrôle échoue, un autre lot a des fichiers indexés : attends une minute et recommence, ne désindexe jamais ce qui n'est pas à toi. Écris ton entrée DONE juste avant ; si `docs/DONE.md` porte aussi l'entrée pas encore commitée d'un autre lot, commite quand même et signale-le dans ta réponse. Message en français, préfixe conventionnel (`fix(...)`, `refactor(...)`, `chore(...)`, `feat(...)`), une ligne, sans accents. Les hooks lefthook formatent et lintent ce qui est indexé : si le lint bloque, corrige et recommite. Pas de `--amend` sur un commit qui n'est pas le tien.
4. Pas de push.
5. Ta réponse finale tient en UNE ligne, rien d'autre : `Demande <lot> : commit hash <hash>` (`<lot>` = le code de ta section, ex. B2). Le résumé — fait, pourquoi, vérifié comment, laissé et pourquoi — va dans ton entrée DONE, pas dans ta réponse. Bloqué sur une décision : une ligne aussi, `Demande <lot> : bloque — <la question, en une phrase, avec ta recommandation>`.

Tâche :
Revue d'extraction de l'admin (`src/components/admin/ExtractorReview.tsx`, moteur `datagen/extractor/review.ts` et `datagen/extractor/core/changes.ts`) : un perso déjà intégré dont le jeu change un détail passe en `diff` (rouge), et le seul geste par ligne est « Intégrer », qui refait toute l'intégration. Retours de Sevih le jour du patch du 06/10/2026 : (1) un costume déplacé (ordre `sort`) ou un costume ajouté ne devrait pas demander une ré-intégration, c'est mineur ; (2) un nom ou une description qui change de mots, sans toucher ni aux buffs ni aux dégâts, c'est une coquille, pas un écart — ça devrait passer tout seul. Et « Valider toute l'extraction » écrit le fichier mais ne met pas en place les images d'un nouveau costume : c'est pour les voir qu'il ré-intègre.

Lis d'abord, en entier : `datagen/extractor/core/changes.ts` (`normalizeTypo`, `isTypoField`, `isTypoEntity`, `diffBuckets`), `datagen/extractor/review.ts` (`reviewEntities`, `acceptTarget`, `acceptTypos`), `datagen/extractor/targets.ts`, `datagen/extractor/integrate.ts` (ce que fait une intégration, surtout l'étape 5, le staging d'images : `characterAssetRequests` + `stageAssets`), `datagen/assets/manifest.ts` autour de `characterAssetRequests` (dont les full arts de costume), `datagen/promote.ts` (la promotion globale, la garde perso), `src/components/admin/ExtractorReview.tsx` et `src/app/api/admin/review/[id]/route.dev.ts`, et leurs tests (`changes.test.ts`, `review.test.ts`, `integrate.test.ts`, `promote.test.ts`).

À faire :
1. UNE TROISIÈME CLASSE D'ÉCART, « mineur », à côté de typo : une entité dont TOUS les champs changés sont mineurs se classe `minor`. Est mineur :
   - un champ typo (règle actuelle, inchangée) ;
   - un champ de TEXTE — nom, titre, description, info-bulle, lore, nom de costume : une chaîne ou un dictionnaire de langues (`en/fr/jp/kr/zh/es`) — dont les NOMBRES n'ont pas bougé : compare les suites de chiffres (avec `%`, `.`, `,` intérieurs) dans l'ordre, entre l'ancien et le nouveau, langue par langue ; même suite = reformulation ; une suite différente = vrai écart (une description de compétence dont un pourcentage change dit un équilibrage, même si la table des valeurs n'est pas dans l'entité) ;
   - un champ sous `costumes` d'un perso : ajout d'un costume, ordre (`sort`), texte d'un costume — toujours mineur ; un costume RETIRÉ n'est pas mineur (le jeu retire rarement, et un visuel disparaît).
   Rien d'autre n'est mineur : stats, valeurs de compétence, buffs, équipement exclusif, éléments, classes, tags, dates, ids — un champ dont la clé n'est pas un champ de texte reste un vrai écart même si sa valeur ressemble à du texte. Décide la liste des clés de texte en lisant les specs (`datagen/extractor/specs/*.ts`) et les cibles, et écris-la à UN endroit, commentée ; en cas de doute sur un champ, il n'est PAS mineur. `isTypoEntity` reste pour la compatibilité, `isMinorEntity` l'englobe.
2. REVUE : statut `minor` dans `ReviewEntityStatus`, compteur dans `DiffBuckets`, badge dans l'écran (couleur discrète, libellé « mineur »), filtre. Le bouton « Corriger les typos » devient « Appliquer les retouches mineures » et applique typo ET mineur (`acceptMinor`, qui remplace `acceptTypos` ; garde `acceptTypos` si un appelant en dépend). L'écran dit combien d'entités de chaque sorte il a appliquées.
3. IMAGES : après `acceptMinor` ET après `acceptTarget` sur la cible des persos, mets en place les images manquantes des persos dont l'entrée a changé — la même étape 5 que l'intégration (`characterAssetRequests` → `stageAssets`), restreinte à ces ids, jamais toute la collecte. Même chose dans `promote --apply` (CLI) pour les persos intégrés dont l'entrée change dans `characters.json` : les images d'un costume nouveau doivent exister sans qu'on ré-intègre personne. La garde perso ne bouge pas : un perso NON intégré n'est jamais ni promu ni stagé par ces chemins.
4. Tests : classification (texte reformulé = mineur ; même texte avec un nombre changé = diff ; costume ajouté ou réordonné = mineur ; costume retiré = diff ; une stat = diff même si la valeur est une chaîne), `acceptMinor` sur un committé factice (n'écrit que les entités mineures), staging restreint aux ids changés (chemins injectables, comme `integrate.test.ts`).

Vérifie à la main, sans écrire dans `data/generated` : `pnpm datagen:build` tourne déjà ce 06/10, la proposition est dans `data/extracted` — lance la revue de la cible des persos en lecture (fonction `reviewEntities` dans un script jetable, ou la page admin si un serveur écoute sur :3000, en lecture seule) et cite dans ton entrée DONE combien d'entités passent de `diff` à `minor` et lesquelles ; relis-en trois pour confirmer que ce sont bien des retouches.

Hors périmètre : la garde perso de `promote.ts`, l'intégration elle-même, les monstres et l'équipement (même mécanique possible plus tard, note-le dans DONE), tout ce qui touche le calculateur.

Ce lot tourne APRÈS F13 (qui tourne seul), avec aucun autre lot sur `datagen/extractor/` ou `src/components/admin/`.
```
