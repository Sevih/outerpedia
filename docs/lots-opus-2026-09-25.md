# Lots pour agents — mode d'emploi

> Comment déléguer un item du [TODO](./TODO.md) à un agent : un prompt complet
> par lot, écrit ici, lancé par le message type, relu avant d'être rangé. Ce
> fichier ne garde que l'outil ; un lot fait sort d'ici, sa trace est dans
> [DONE.md](./DONE.md) (64 lots du 25/09 au 04/10/2026, table des commits et
> leçons aux entrées du 04/10).
>
> Code d'un lot : A = une heure ou moins, B = une demi-journée, C = une
> journée, F = demande du jugement (agent Fable). Plusieurs lots tournent
> ensemble tant qu'ils ne touchent pas les mêmes fichiers ; ceux qui écrivent
> les six locales, les mêmes gros fichiers, ou qui lancent `datagen:build`
> passent un par un.

## Lancement — message type (le numéro du lot en dernier mot, sans point final)

Un agent ne lit que ce fichier : les règles communes sont dans le préambule de
chaque prompt, la réponse attendue aussi. Message à coller tel quel, en
remplaçant le dernier mot :

```text
Ouvre /home/sevih/Documents/Projet perso/outerpedia/docs/lots-opus-2026-09-25.md et lis UNIQUEMENT la section du lot dont le code est le dernier mot de ce message (ne lis pas les autres lots). Fais tout ce que son bloc demande, préambule compris. Ta réponse finale tient en une seule ligne : Demande <lot> : commit hash <hash>. Lot à faire : B2
```

Réponse attendue : `Demande B2 : commit hash 1a2b3c4d`. Tout le reste (résumé,
vérifications, ce qui est laissé) est dans l'entrée DONE du commit, c'est là
que la relecture le lit. Un agent bloqué répond `Demande B2 : bloque — …` avec
sa question et sa recommandation en une phrase.

## F11 · Portraits animés : un contexte WebGL partagé par toutes les cartes

```text
Tu travailles dans le dépôt `outerpedia` (Next.js + pipeline datagen), à la racine du projet, sur la branche `main`. Avant de toucher au code, lis `CONVENTIONS.md` et `CLAUDE.md` et respecte-les. Ce qui suit répond d'avance aux questions habituelles : ne les repose pas, applique.

Périmètre et méthode
- Périmètre STRICT à la tâche ci-dessous. Pas de refactor à côté, pas de « pendant que j'y suis ». Ce que tu repères hors périmètre va dans ton résumé, pas dans le diff.
- D'autres fichiers modifiés ou non suivis peuvent apparaître dans le working tree pendant ta session : ce sont d'autres lots qui tournent en parallèle. Ne les touche pas, ne les indexe pas, ne les signale pas, c'est attendu.
- Si la tâche cache une décision (métier, comportement ambigu, ordre de référence inconnu), arrête-toi AVANT de modifier quoi que ce soit et pose UNE question précise avec ta recommandation. Ne tranche pas toi-même.
- Toute clé i18n ajoutée l'est dans les SIX locales `src/i18n/locales/{en,fr,es,jp,kr,zh}.ts` (`keys.test.ts` exige la parité). Cherche une clé existante avant d'en créer une. Pour jp/kr/zh, traduction sobre ; en cas de doute, l'anglais, signalé dans le résumé.
- Ne touche jamais à `package.json` ni à `pnpm-lock.yaml`. Une version à monter ou à descendre est une décision : arrête-toi et pose la question (une montée de `next` validée sur typecheck, lint et tests a fait tomber la prod le 25/09).
- Ne lance jamais `pnpm dev`, `pnpm install`, `lefthook install`, ni un `git worktree add`. Si un serveur écoute déjà sur :3000, tu peux le lire avec `curl`. Si ta tâche exige de tester un hook git (commit d'essai, changement de branche), NE LE FAIS PAS toi-même : d'autres agents peuvent avoir des fichiers indexés dans cette arborescence et ton commit d'essai les emporterait. Prépare le changement, décris le test à faire, et laisse Sevih le jouer.

Vérification (obligatoire avant de rendre)
- `pnpm typecheck`, `pnpm lint`, `pnpm test` doivent passer. Cite la dernière ligne de chacun dans ton résumé.
- Aucun changement visuel non demandé ; quand la tâche en interdit, dis ce que tu as comparé.

Livraison (fais-la toi-même, sans demander)
1. Entrée dans `docs/DONE.md`, en TÊTE de la section du jour (`## 2026-MM-JJ`, crée-la si elle manque, sous le préambule du fichier) : une puce, titre en gras, puis le quoi, le pourquoi, le comment, la vérification, et ce que tu as laissé — dans le style des entrées voisines (français, prose dense, noms de fichiers en backticks).
2. Si l'item existe dans `docs/TODO.md`, retire-le (ou marque « FAIT » et ce qui reste, si la ligne porte d'autres points).
3. Commit par toi, en indexant EXPLICITEMENT et uniquement tes fichiers plus `docs/DONE.md` (et `docs/TODO.md` si touché). Jamais `git add -A`, jamais `git add .`. L'index git est PARTAGÉ avec les autres lots : indexe et commite dans UNE SEULE commande shell, précédée d'un contrôle — `test -z "$(git diff --cached --name-only)" && git add <tes chemins> && git commit -m "…"`. Si le contrôle échoue, un autre lot a des fichiers indexés : attends une minute et recommence, ne désindexe jamais ce qui n'est pas à toi. Écris ton entrée DONE juste avant ; si `docs/DONE.md` porte aussi l'entrée pas encore commitée d'un autre lot, commite quand même et signale-le dans ta réponse. Message en français, préfixe conventionnel (`fix(...)`, `refactor(...)`, `chore(...)`, `feat(...)`), une ligne, sans accents. Les hooks lefthook formatent et lintent ce qui est indexé : si le lint bloque, corrige et recommite. Pas de `--amend` sur un commit qui n'est pas le tien.
4. Pas de push.
5. Ta réponse finale tient en UNE ligne, rien d'autre : `Demande <lot> : commit hash <hash>` (`<lot>` = le code de ta section, ex. B2). Le résumé — fait, pourquoi, vérifié comment, laissé et pourquoi — va dans ton entrée DONE, pas dans ta réponse. Bloqué sur une décision : une ligne aussi, `Demande <lot> : bloque — <la question, en une phrase, avec ta recommandation>`.

Tâche :
Le chantier de fond de l'audit des portraits animés : UN contexte WebGL pour toutes les cartes, au lieu d'un par carte. Lis d'abord, en entier : `docs/audit/portrait-fx.md` (P2 pour le pourquoi, P5, P6 et P10 pour ce que le chantier emporte ou croise), l'en-tête de `src/components/character/portrait-fx-gl.ts` (la lumière linéaire, les trois faits mesurés sur la perte de contexte, les deux écarts assumés), `AnimatedPortrait.tsx` (observateur partagé, `LIVE_CAP`, éviction), `portrait-fx-sim.ts`, `portrait-fx.ts`, `SettingsPortrait.tsx`, la page `src/app/dev/AnimatedPortrait/page.dev.tsx`, et dans `docs/DONE.md` les entrées des lots F4, B15, F8, F9, F10 (03 et 04/10) — elles disent ce qui a été mesuré, comment, et ce qui a déjà mordu.

L'état d'aujourd'hui : chaque carte animée crée son contexte WebGL2 sur son propre canvas, y recharge et y monte SA copie de toutes ses textures (3 Mo par carte `_Demi`, l'effet de 16 persos), et un plafond de 8 contextes vivants (`LIVE_CAP`) évince puis ressuscite les cartes au fil du scroll. Le plafond se dépasse dès que plus de huit cartes sont à l'écran (12 sur `/characters` trié par sortie), et tout le code de perte/résurrection (`RESTORABLE`, `LOSE_EXT`, `restoreContext`) n'existe que pour ça.

La cible :
1. UN contexte WebGL2 pour la page, créé à la première carte animée qui entre à l'écran, jamais avant (réglage éteint ou aucun perso à effet = aucun contexte, aucune boucle, comme aujourd'hui). Programmes compilés une fois, CHAQUE texture montée une fois quelle que soit le nombre de cartes qui la lisent (effets ET art du portrait), avec une règle de libération que tu choisis et que tu écris (une carte démontée ne doit pas laisser ses textures pour toujours sur une page qui change de filtre).
2. Chaque carte garde un canvas à elle, mais en 2D : le moteur rend la carte dans le contexte partagé puis reporte le résultat dans son canvas (`drawImage` dans la même tâche que le rendu, ou `ImageBitmap`/`bitmaprenderer` — à toi de choisir, mesure à l'appui, et de dire pourquoi). La taille, le débord (`fxBleed`), le `SUPERSAMPLE`, le plafond de dpr restent ceux d'aujourd'hui.
3. UNE boucle `requestAnimationFrame` pour toutes les cartes visibles, arrêtée quand aucune ne l'est, quand l'onglet est caché, et après une image sous `prefers-reduced-motion`.
4. `LIVE_CAP`, l'éviction et la résurrection par carte disparaissent ; l'observateur partagé reste et ne décide plus que de qui est dessiné. La perte du contexte unique par le NAVIGATEUR (retour d'onglet, reset du pilote) reste un cas normal : tout se reconstruit depuis les caches CPU, sans repasser par le réseau, et les cartes gardent leur dernière image en attendant.
5. Le repli ne change pas : sans WebGL2, ou sur un effet refusé, le `<img>` de `Portrait` reste visible sous le canvas — et le refus est loggé UNE fois, pas une fois par carte et par passage (c'est P6 : traite-le ici, il tombe avec le chantier).

Ce qui ne doit PAS bouger :
- L'image. Même shader, même ordre d'opérations, même chaîne linéaire → sRGB, mêmes graines (`mountSeeds`), mêmes tailles. Attention à ce que le report ajoute : alpha prémultiplié entre le tampon WebGL et le canvas 2D, encodage sRGB fait une seule fois, bords du débord transparents. Un écart de couleur ou de frange ici est LE risque du lot.
- Le contrat des données. `portrait-fx.json`, `extract-portrait-fx.py`, les types de `portrait-fx.ts` et les refus de `layerVerdict` ne changent pas : Sevih ajoute un effet quand un nouveau perso en apporte un (régénérer la table, parfois transcrire une branche du shader), et ce geste doit rester exactement le même. Écris dans ton entrée DONE, en trois lignes, où se fait cet ajout après ton passage.
- L'API vue des pages : `AnimatedPortrait` et ses props (`effect`, `fxId`, `onFxError`, `fxEmitters`, `fxTexCap`), `SettingsPortrait`, le chunk paresseux, la page `/dev/AnimatedPortrait` et ses sections (elle sert de banc : adapte-la si une section mesurait les contextes par carte, ne la vide pas).
- Hors périmètre : P3, P7, P8 (extraction et gardes), l'instanciation des billboards et les autres leviers de P10. Tu peux solder P9 et la dette UNIQUEMENT sur les lignes que tu réécris (les commentaires de l'en-tête sur l'éviction et la résurrection deviennent faux : réécris-les, ne les laisse pas mentir).

Vérification propre au lot — personne d'autre ne regardera l'écran avant le commit, donc c'est toi :
- Si un serveur écoute sur :3000 (Sevih le laisse ouvert pour toi ; ne le lance pas, et lis les pages une par une), mesure dans Firefox sans tête comme les lots F4, F8 et B15 l'ont fait (profil jetable, WebDriver BiDi, `/dev/AnimatedPortrait`). AVANT d'écrire une ligne, capture la référence : temps et aléa figés, tampons des canvas lus au pixel, pour chaque effet de la table. APRÈS : mêmes captures, différence au pixel. Attendu : identique, ou un écart que tu expliques et chiffres (max sur 255, part des pixels touchés). Un écart visible que tu n'expliques pas = pas de commit.
- Compte, avant et après : contextes créés et vivants en défilant toute la page (attendu après : 1), montages de texture par URL (attendu : 1), appels de `draw` par seconde, et le temps d'une image avec 4 puis 12 cartes à l'écran. Si le report coûte plus cher que l'ancien rendu au point de perdre les 60 images/s là où elles tenaient, ne commite pas : réponds `bloque` avec les chiffres et ta recommandation.
- Rejoue le scénario de F8 (descente lente puis saut en haut) : plus aucune carte éteinte. Simule une perte du contexte unique (`WEBGL_lose_context`) : toutes les cartes reviennent.
- Si rien n'écoute sur :3000, ne code pas à l'aveugle : réponds `bloque — pas de serveur sur :3000`.
- Tests : ce qui devient pur (cache de textures et sa règle de libération, ordonnanceur de la boucle, choix des cartes à dessiner) est testé ; le rendu GL lui-même ne l'est pas, dis-le.
- Dans ton entrée DONE : le tableau avant/après, ce que Firefox ne prouve pas (Chrome, Safari, un téléphone — aucun des trois sur ce poste), et le scénario de contrôle que Sevih jouera sur Chrome ET Firefox : réglage allumé, `/characters` trié par sortie, défilement jusqu'en bas et retour, changement de filtre, onglet caché puis revenu, comparaison d'une carte `_Demi` avec la prod.
- Retire l'item du TODO ; s'il reste des constats Basse ouverts (P7, P8, P10), laisse-les dans une ligne à part.

Ce lot tourne SEUL : il réécrit `portrait-fx-gl.ts` et `AnimatedPortrait.tsx`.
```
