# Lots pour agents — mode d'emploi

> Comment déléguer un item du [TODO](./TODO.md) à un agent : un prompt complet
> par lot, écrit ici, lancé par le message type, relu avant d'être rangé. Ce
> fichier ne garde que l'outil ; un lot fait sort d'ici, sa trace est dans
> [DONE.md](./DONE.md) (90 lots du 25/09 au 07/10/2026, table des commits et
> leçons aux entrées du 04/10).
>
> Code d'un lot : A = une heure ou moins, B = une demi-journée, C = une
> journée, F = demande du jugement (agent Fable). Plusieurs lots tournent
> ensemble tant qu'ils ne touchent pas les mêmes fichiers ; ceux qui écrivent
> les six locales, les mêmes gros fichiers, ou qui lancent `datagen:build`
> passent un par un.

## Lancement — message type (le numéro du lot en dernier mot, sans point final)

Un agent ne lit que ce fichier : les règles communes sont dans le préambule de
chaque prompt, la réponse attendue aussi. Message à coller tel quel, en
remplaçant le dernier mot :

```text
Ouvre /home/sevih/Documents/Projet perso/outerpedia/docs/lots-opus-2026-09-25.md et lis UNIQUEMENT la section du lot dont le code est le dernier mot de ce message (ne lis pas les autres lots). Fais tout ce que son bloc demande, préambule compris. Ta réponse finale tient en une seule ligne : Demande <lot> : commit hash <hash>. Lot à faire : B2
```

Réponse attendue : `Demande B2 : commit hash 1a2b3c4d`. Tout le reste (résumé,
vérifications, ce qui est laissé) est dans l'entrée DONE du commit, c'est là
que la relecture le lit. Un agent bloqué répond `Demande B2 : bloque — …` avec
sa question et sa recommandation en une phrase.

## Cap de quick (décision de Sevih du 07/10/2026)

`pnpm quick` (`scripts/quick/`) doit remplacer, à terme, tout ce qui dans
l'admin ne demande pas d'extraction : les éditeurs (persos, événements,
bannières, changelog, presets d'équipement, tags, effets…), les outils et
l'éditeur de guides — tout sauf les catégories « extractor » et « misc ». La
série UI de quick (C4, C5, B30, F16, B28, B29, C6, tous le 07/10) a posé ce
terrain : un menu horizontal à DEUX NIVEAUX (les groupes en haut — Publication,
Données, puis Éditeurs, Guides, Outils — et les sections du groupe en dessous ;
décision de Sevih du 07/10 : pas de barre latérale), une section = ses fichiers
`scripts/quick/ui/tabs/<nom>.{html,js,css}` et une entrée du tableau `GROUPS`
de `lib.js`, la charte dans `scripts/quick/ui/STYLE.md`, le banc de captures
`node scripts/quick/shot.mjs`. Un lot qui ajoute une section lit STYLE.md
d'abord et ne touche qu'à ses fichiers.

## C9 · Gear reco : aperçu pré-rendu des builds et de la note, comme la fiche perso (Opus, après C8)

Point 3 du retour de Sevih du 07/10 : « on n'a pas de visuel pré-rendu, donc impossible de savoir si la syntaxe est bonne (même chose pour la note) ». Tourne SEUL. C8 est commité (`e00184bf`, relu) : `gear-view.mjs` et les options enrichies sont en place.

```text
Tu travailles dans le dépôt `outerpedia` (Next.js + pipeline datagen), à la racine du projet, sur la branche `main`. Avant de toucher au code, lis `CONVENTIONS.md` et `CLAUDE.md` et respecte-les. Ce qui suit répond d'avance aux questions habituelles : ne les repose pas, applique.

Périmètre et méthode
- Périmètre STRICT à la tâche ci-dessous. Pas de refactor à côté, pas de « pendant que j'y suis ». Ce que tu repères hors périmètre va dans ton résumé, pas dans le diff.
- D'autres fichiers modifiés ou non suivis peuvent apparaître dans le working tree pendant ta session : ce sont d'autres lots qui tournent en parallèle. Ne les touche pas, ne les indexe pas, ne les signale pas, c'est attendu.
- Si la tâche cache une décision (métier, comportement ambigu, ordre de référence inconnu), arrête-toi AVANT de modifier quoi que ce soit et pose UNE question précise avec ta recommandation. Ne tranche pas toi-même.

- Ne touche jamais à `package.json` ni à `pnpm-lock.yaml`. Une version à monter ou à descendre est une décision : arrête-toi et pose la question (une montée de `next` validée sur typecheck, lint et tests a fait tomber la prod le 25/09).
- Ne lance jamais `pnpm dev`, `pnpm install`, `lefthook install`, ni un `git worktree add`. Si un serveur écoute déjà sur :3000, tu peux le lire avec `curl`. Si ta tâche exige de tester un hook git (commit d'essai, changement de branche), NE LE FAIS PAS toi-même : d'autres agents peuvent avoir des fichiers indexés dans cette arborescence et ton commit d'essai les emporterait. Prépare le changement, décris le test à faire, et laisse Sevih le jouer.

Vérification (obligatoire avant de rendre)
- `pnpm typecheck`, `pnpm lint`, `pnpm test` doivent passer. Cite la dernière ligne de chacun dans ton résumé.
- Aucun changement visuel non demandé ; quand la tâche en interdit, dis ce que tu as comparé.

Livraison (fais-la toi-même, sans demander)
1. Entrée dans `docs/DONE.md`, en TÊTE de la section du jour (`## 2026-MM-JJ`, crée-la si elle manque, sous le préambule du fichier) : une puce, titre en gras, puis le quoi, le pourquoi, le comment, la vérification, et ce que tu as laissé — dans le style des entrées voisines (français, prose dense, noms de fichiers en backticks).
2. Si l'item existe dans `docs/TODO.md`, retire-le (ou marque « FAIT » et ce qui reste, si la ligne porte d'autres points).
3. Commit par toi, en indexant EXPLICITEMENT et uniquement tes fichiers plus `docs/DONE.md` (et `docs/TODO.md` si touché). Jamais `git add -A`, jamais `git add .`. L'index git est PARTAGÉ avec les autres lots : indexe et commite dans UNE SEULE commande shell, précédée d'un contrôle — `test -z "$(git diff --cached --name-only)" && git add <tes chemins> && git commit -m "…"`. Si le contrôle échoue, un autre lot a des fichiers indexés : attends une minute et recommence, ne désindexe jamais ce qui n'est pas à toi. Écris ton entrée DONE juste avant ; si `docs/DONE.md` porte aussi l'entrée pas encore commitée d'un autre lot, commite quand même et signale-le dans ta réponse. Message en français, préfixe conventionnel (`fix(...)`, `refactor(...)`, `chore(...)`, `feat(...)`), une ligne, sans accents. Les hooks lefthook formatent et lintent ce qui est indexé : si le lint bloque, corrige et recommite. Pas de `--amend` sur un commit qui n'est pas le tien.
4. Pas de push.
5. Ta réponse finale tient en UNE ligne, rien d'autre : `Demande <lot> : commit hash <hash>` (`<lot>` = le code de ta section, ex. B2). Le résumé — fait, pourquoi, vérifié comment, laissé et pourquoi — va dans ton entrée DONE, pas dans ta réponse. Bloqué sur une décision : une ligne aussi, `Demande <lot> : bloque — <la question, en une phrase, avec ta recommandation>`.

Tâche :
Dans `pnpm quick` (`scripts/quick/`), l'onglet « Gear reco » (`scripts/quick/ui/tabs/gear.{html,js,css}`, modules purs `scripts/quick/ui/gear-sets.mjs` et `gear-view.mjs`, `scripts/quick/actions.ts`, routes `/api/gear-reco*` de `server.ts`) édite les builds de `data/curated/gear-reco.json` sans montrer ce que la fiche perso en fera : les balises inline de la note (`{B/…}`, `{I-W/…}`, …) et les références des pièces ne se voient qu'au contrôle d'« Enregistrer », et le rendu, jamais. Lis d'abord les entrées DONE du 07/10 des lots C7 et C8 et leurs relectures, puis `scripts/quick/ui/STYLE.md`, puis le code de l'onglet, puis `scripts/quick/env.ts` (quick se déclare en développement : `IS_DEV` est vrai dans son processus — la leçon du lot B31). Côté site : `src/lib/admin/gear-preview-actions.ts` (`previewGearReco(builds, lang)` : l'aperçu de l'ADMIN — il résout les builds avec le vrai résolveur et renvoie des DONNÉES pures : `PreviewBuild[]` avec `noteSegments`, et les `labels` traduits), `src/components/character/GearRecoSection.tsx` (ce que la fiche perso affiche : rangées Weapon / Accessory / Talisman / Armor Set, `ItemRow`, `ComboLineView`, légende des bonus de set, priorité de substats, bande de note), `src/components/admin/InlinePreview.tsx` et `src/lib/parse-text.tsx` (le type `InlineSegment` : text, br, unknown, icon, effect, item, stat — et les classes de couleur qu'il porte : `text-buff`, `text-debuff`, `text-class`, `text-equipment`, `text-highlight`, `text-item-*`), `src/components/ui/GameText.tsx` (`renderGameColors` : les balises `<color=#…>…</color>` du jeu), `src/lib/stats.ts` (`STAT_ICON`), `src/app/globals.css` (les jetons de ces couleurs).

Objectif.

1. Une route `POST /api/gear-reco/preview` dans `server.ts`, corps `{ builds, lang }` (les builds tels que `gToBuild` les envoie à l'enregistrement, `lang` une langue du site), qui répond `previewGearReco(builds, lang)` : `{ builds: PreviewBuild[], labels }`. Appelle la fonction du site telle quelle (c'est un module `'use server'`, mais dans le processus de quick c'est une fonction async ordinaire ; `IS_DEV` y est vrai grâce à `env.ts` — vérifie-le, et si quelque chose l'empêche, extrais la partie pure dans un module importé des deux côtés plutôt que de la recopier). Un build invalide (id inconnu, preset absent, nom vide) ne fait pas tomber le serveur : la route répond 400 `{ error }` si la résolution lève, sinon 200 avec ce qui a été résolu (le résolveur marque les pièces inconnues `unresolved`). `GET /api/gear-reco/state` expose en plus `statIcons` (la table `STAT_ICON`), pour les puces de stat principale.

2. Dans la page, chaque carte de build porte en bas un bloc « Aperçu » (dépliable, ouvert par défaut, sans persistance) qui montre le build COMME LA FICHE PERSO le montrera, à partir de la réponse de la route : les rangées étiquetées par les `labels` reçus — Weapon / Accessory / Talisman avec, par pièce, la tuile de `gear-view.mjs` (44 px) et le nom coloré par le grade, les puces de stat principale (icône `images/ui/stat/<sprite>.webp` + abréviation) ; Armor Set en rangées de combos comme `ComboLineView` puis la légende des bonus (nom du set — texte 2p / 4p, `<color=#…>` rendu en span coloré comme `renderGameColors`, `\n` littéraux en sauts de ligne) ; la priorité de substats en texte ; puis la note rendue depuis `noteSegments` : `text` tel quel, `br`, `unknown` en ROUGE (c'est l'alerte de syntaxe que Sevih demande), `icon` = icône + libellé dans sa couleur, `effect` = tuile d'effet (teinte buff ou debuff, jetons `--buff-bg` / `--debuff-bg`) + libellé, `item` = icône + nom coloré par le grade, `stat` = icône + nom ; la `desc` d'un segment va dans un `title`, pas de tooltip ni de lien (rien n'est cliquable dans l'aperçu). Une pièce `unresolved` s'affiche en rouge avec son id, comme `ItemRow`. Les classes de couleur des segments sont traduites en jetons recopiés de `globals.css` sous les mêmes noms dans `gear.css` (`--buff`, `--debuff`, `--class`, `--equipment`, `--highlight`, et les `--item-*` posés par C8) — règle de STYLE.md. La LANGUE de l'aperçu se choisit par un groupe segmenté (les six langues du site, `en` par défaut) posé une fois pour toutes les cartes dans la barre d'enregistrement ; la note d'un build sans texte dans cette langue montre ce que le site montrera (le repli, c'est le résolveur qui le fait).

3. Rafraîchissement : à chaque changement d'un build du perso (toute action qui passe par `gTouched`/`gRedraw`, et la frappe dans la note ou le nom, avec un délai de 400 ms après la dernière frappe), UNE requête pour tous les builds du perso (`gBuilds.map(gToBuild)`), rendue carte par carte ; pendant la requête le bloc garde le rendu précédent atténué (`.busy`) ; une réponse 400 ou un échec réseau affiche l'erreur en rouge dans le bloc ; une réponse arrivée après une requête plus récente est ignorée (compteur, comme `gSeq`). Le constructeur HTML de l'aperçu est PUR et vit dans `gear-view.mjs` (il reçoit un `PreviewBuild`, les `labels`, `statIcons`, `imgBase`), testé : un segment `unknown` donne un élément de classe rouge, un segment `item` donne l'icône et le nom dans la classe du grade, un `br` donne un `<br>`, un bonus de set avec `<color=#ff0000>x</color>` donne un span coloré, une pièce `unresolved` est rouge.

Hors périmètre : l'éditeur lui-même (pickers, bascules, note, « Traduire »), le panneau de verdict des substats du site, les onglets de builds (une carte = un aperçu), les tooltips, l'admin et le site.

Décisions déjà prises (ne les repose pas) : l'aperçu est par carte et ouvert par défaut ; une seule langue d'aperçu pour tout l'onglet, `en` par défaut ; le délai est de 400 ms ; aucun lien dans l'aperçu.

Vérification propre au lot : outre typecheck, lint et tests, (a) la route en direct sur un quick isolé (`DISCORD_BOT_TOKEN= DEV_PEERS= QUICK_PORT=<un autre port> pnpm quick --no-open`, JAMAIS un enregistrement réel : chaque enregistrement de quick committe ET pousse `main`) : `curl` avec les builds d'Aer (`GET /api/gear-reco/state?id=2000055`, ou la forme que la route prend pour un perso) → des `noteSegments` et des `labels` en `fr` ; puis un build dont la note porte `{B/nope}` → un segment `unknown` ; puis un corps vide ou un build sans nom → 400, et le serveur répond encore ; (b) le banc : `node scripts/quick/shot.mjs --port <port> --tabs gear --out /tmp/quick-shots/c9 --hash gear/2000055` — le bloc d'aperçu sous la carte, tuiles, rangée de combo, légende, note. Cite les chemins des PNG dans ton entrée DONE.

Ne tourne avec aucun autre lot qui touche `scripts/quick/`, et pas avant le commit de C8.
```
